# Tasks

Every task is test-first. Write the failing test, run it, and confirm it fails for the intended reason: a compile error is not a red step. Then implement, then refactor with the tests green. Where a test pins behaviour that already holds, the red step is a temporary inversion of the implementation that the test must notice. The inversion is undone by editing the file back, never by a discarding git command.

## 4. Lockout reports through the policy's recording view

- [ ] 4.1 Add the report type and its kinds (`Locked`, `Ceiling`, `Cleared`), `WithLockoutObserver`, and the method that returns the policy's `AttemptStore` view (design decision 5; names are provisional). Without an observer the view passes every call through. Red: a test with a mocked store (`use-mockgen`) expecting exactly one `RecordFailure` and no `FailureCount` when no observer is configured, and a construction test that a nil observer is a configuration error. Verify: `go test -count=1 -run 'TestLockoutObserver|TestNewAccountLockoutPolicy' ./policy/`.
- [ ] 4.2 With an observer, each recorded failure that leaves the identifier locked is reported, as `Ceiling` at or above the ceiling and `Locked` at or above the threshold, including under the sliding lock. Each report carries the identifier as submitted, the count and the instant. A failed write is not reported. Unknown and known identifiers are reported in the same form. Red: a table test (`table-test`) covering the spec scenarios "Threshold reached", "Each further locking failure is reported", "Ceiling reached" and "Unknown and known identifiers are reported alike", plus a store-error case. Then a concurrency test: N goroutines each record one failure past the threshold, and every one of them is reported. Verify: `go test -race -count=1 -run 'TestLockoutObserver' ./policy/`.
- [ ] 4.3 `Reset` through the view reports `Cleared` only when the count before it was above zero, and only after the reset succeeds. Red: table cases for the spec scenarios "Cleared" and "Clearing nothing is not reported", plus a reset error, which is not reported. Verify: `go test -count=1 -run 'TestLockoutObserver' ./policy/`.
- [ ] 4.4 A panicking observer is recovered and logged with fixed text, and the view's return value is unchanged. The log goes through `WithLockoutLogger`, whose default is `slog.Default()` and which ignores a nil logger, as `WithMFAPolicyLogger` does. Red: a test whose observer panics, asserting that `RecordFailure` returns nil and that one record is written to a consumer logger. Verify: `go test -count=1 -run 'TestLockoutObserver' ./policy/`.
- [ ] 4.5 Godoc on the observer, the view and the report says that the observer sees only what goes through the view. `FormLoginDeps.Attempts` and `BasicAuthDeps.Attempts` recommend the policy's view. Add an `Example` that wires the view into form login. Verify: `go test -count=1 -run Example ./policy/ ./httpsec/`, plus `go doc ./httpsec FormLoginDeps` and `go doc ./httpsec BasicAuthDeps`.
