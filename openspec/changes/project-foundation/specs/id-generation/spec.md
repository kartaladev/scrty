## Purpose

Gives every record scrty owns a sortable, collision-resistant identifier with stable text, JSON and SQL encodings, generated by a default UUIDv7 generator that consumers can replace.

## ADDED Requirements

### Requirement: Default identifiers are RFC 9562 UUIDv7
The default generator SHALL produce identifiers that conform to RFC 9562 version 7: the version field SHALL be `7`, the variant field SHALL be the RFC 9562 variant (`10` in binary), and the leading 48 bits SHALL hold the Unix time in milliseconds at which the identifier was generated.

#### Scenario: Version, variant and timestamp are set
- **WHEN** the default generator creates an identifier while its time source reads 2022-02-22T19:22:22Z
- **THEN** the identifier's version field is `7`
- **AND** its variant field is binary `10`
- **AND** its leading 48 bits equal the Unix millisecond timestamp 1645557742000

### Requirement: Identifiers from one generator are strictly increasing
Identifiers created by a single generator SHALL be strictly increasing, both as 16-byte values compared bytewise and as canonical strings compared lexically. This SHALL hold for identifiers created within the same millisecond, for identifiers created concurrently from multiple goroutines, and when the time source moves backwards.

#### Scenario: Many identifiers within one millisecond
- **WHEN** a generator whose time source is frozen at one millisecond creates 100,000 identifiers
- **THEN** each identifier is greater than the one created before it, bytewise and as a canonical string

#### Scenario: Time source moves backwards
- **WHEN** a generator creates an identifier, its time source then moves one second backwards, and it creates another identifier
- **THEN** the second identifier is greater than the first

#### Scenario: Concurrent generation
- **WHEN** 64 goroutines create identifiers from the same generator at the same time
- **THEN** no two identifiers are equal
- **AND** sorting all of them bytewise gives the same order as sorting them by canonical string

#### Scenario: Later time sorts later across generators
- **WHEN** two independent generators create identifiers at millisecond timestamps T and T+1
- **THEN** the identifier created at T+1 is greater than the identifier created at T

### Requirement: Generation failure is reported, never masked
When a generator cannot obtain the randomness it needs, it SHALL return an error. It SHALL NOT return the zero identifier, a previously returned identifier, or an identifier with less randomness than specified.

#### Scenario: Random source fails
- **WHEN** a generator is configured with a random source that returns an error
- **THEN** creating an identifier returns an error that wraps the random source's error
- **AND** no identifier is returned

### Requirement: The zero identifier means "no identifier"
The all-zero identifier SHALL report itself as zero, and SHALL be the only identifier that does. No generator shipped by scrty SHALL return it.

#### Scenario: Zero value
- **WHEN** an identifier variable is declared and not assigned
- **THEN** it reports itself as zero

#### Scenario: Generated identifier
- **WHEN** the default generator creates an identifier
- **THEN** the identifier does not report itself as zero

### Requirement: Canonical text encoding and strict parsing
An identifier's text form SHALL be the 36-character, lowercase, hyphenated RFC 9562 string (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`). Parsing SHALL accept exactly that layout in either letter case, and SHALL reject every other input with an error, including the empty string, braces, a `urn:uuid:` prefix and the 32-character unhyphenated form. Parsing SHALL NOT check the version field, so identifiers from a consumer's generator parse unchanged.

#### Scenario: Round trip
- **WHEN** an identifier is formatted as text and the text is parsed
- **THEN** parsing succeeds and yields an identifier equal to the original

#### Scenario: Uppercase input
- **WHEN** `017F22E2-79B0-7CC3-98C4-DC0C0C07398F` is parsed
- **THEN** parsing succeeds
- **AND** formatting the result yields `017f22e2-79b0-7cc3-98c4-dc0c0c07398f`

#### Scenario: Rejected layouts
- **WHEN** any of `""`, `{017f22e2-79b0-7cc3-98c4-dc0c0c07398f}`, `urn:uuid:017f22e2-79b0-7cc3-98c4-dc0c0c07398f`, `017f22e279b07cc398c4dc0c0c07398f` or `017f22e2-79b0-7cc3-98c4-dc0c0c07398g` is parsed
- **THEN** parsing returns an error that identifies the input as an invalid identifier

#### Scenario: Non-v7 identifier from a consumer
- **WHEN** a valid version 4 UUID string is parsed
- **THEN** parsing succeeds and the identifier keeps its bytes unchanged

### Requirement: JSON encoding
An identifier SHALL encode to JSON as its canonical text form in a JSON string, and SHALL decode only from a JSON string that parses under the text encoding rules. Decoding any other JSON value, including `null` into a non-pointer identifier and the empty string, SHALL fail.

#### Scenario: Encode
- **WHEN** a struct field holding identifier `017f22e2-79b0-7cc3-98c4-dc0c0c07398f` is encoded to JSON
- **THEN** the field's value is the JSON string `"017f22e2-79b0-7cc3-98c4-dc0c0c07398f"`

#### Scenario: Decode invalid JSON value
- **WHEN** the JSON number `42` or the JSON string `""` is decoded into an identifier
- **THEN** decoding returns an error

#### Scenario: Omitted when zero
- **WHEN** a struct field tagged `json:",omitzero"` holds the zero identifier and the struct is encoded to JSON
- **THEN** the field is absent from the output

### Requirement: SQL encoding
An identifier SHALL be writable as a SQL parameter, where it is sent as its canonical text form, which PostgreSQL accepts for both `uuid` and `text` columns. Reading SHALL accept the canonical text form (as a string or bytes) and the 16-byte binary form. Reading SQL `NULL` into an identifier SHALL fail with an error; nullable columns SHALL be read through a nullable wrapper.

#### Scenario: Write then read a native uuid column
- **WHEN** an identifier is inserted into a PostgreSQL `uuid` column and selected back
- **THEN** the identifier read back is equal to the one written

#### Scenario: Read binary form
- **WHEN** a 16-byte value is scanned into an identifier
- **THEN** the identifier holds those 16 bytes in the same order

#### Scenario: Read NULL
- **WHEN** SQL `NULL` is scanned into an identifier
- **THEN** scanning returns an error

#### Scenario: Read malformed value
- **WHEN** a 15-byte value or a malformed string is scanned into an identifier
- **THEN** scanning returns an error and the identifier is unchanged

### Requirement: The generator is replaceable
Any scrty component that creates records with library-owned identifiers SHALL obtain identifiers from a generator it is configured with. When none is configured, it SHALL use the default UUIDv7 generator. A consumer-supplied generator's identifiers SHALL be used exactly as returned, and its errors SHALL be propagated. The default generator's time source and random source SHALL each be replaceable.

#### Scenario: Consumer generator
- **WHEN** a component is configured with a consumer generator that returns identifier `00000000-0000-4000-8000-000000000001`
- **THEN** the record the component creates carries exactly that identifier

#### Scenario: Consumer generator fails
- **WHEN** a component's consumer generator returns an error
- **THEN** the component creates no record and returns an error that wraps the generator's error

#### Scenario: Deterministic default generator
- **WHEN** the default generator is configured with a fixed time source and a fixed random source
- **THEN** two generators configured identically produce the same sequence of identifiers
