## Context

See `proposal.md` for the motivation. Every decision below was made in `release-readiness` (decisions 9–14 there, user's choices of 2026-10-31) and moved here unchanged on 2026-11-02, renumbered 1–6. Only their numbering and this context are new. On 2026-11-03, after `close-security-gaps` was archived, the change was checked against `main`, and its scenarios were swept for gaps. Decisions 3, 5 and 6 gained corrections of fact. Decision 3 also gained the chain's subject option and its build check, a new choice made by the user that day. Decision 2 gained a spec delta. While the change was applied, the same day, decisions 1, 3, 4 and 6 gained further decisions and corrections from reproduced findings. On 2026-11-04 the review of #68 added task group 6, with further additions to decisions 3 and 4. Each addition is dated. Reproductions in review ran as scratch tests that are not kept in the tree; each is named below by the row in the tree that now pins the case, which fails without its code.

- **`notify`.** The queued sender recovers a panic in the wrapped sender, but `recover` cannot stop `runtime.Goexit`. `notify/smtp.go` wraps `ErrConfig` for a message with no sender address.
- **Token subject.** `token` issues the principal's username as `sub` (the package doc, "The subject"). The chain's session-backed bearer interceptor reloads the user by username, keyed on `sub` (`lookupByUsername` in `httpsec/bearer.go`). The standalone `authenticate.JWTAuthenticator` builds its principal from the claims alone.
- **Signing keys.** `signingkey.KeyStore` stores and loads records but cannot delete one. Housekeeping stops publishing old keys and leaves them in the store.
- **Passkeys.** `passkey.CredentialStore.DeleteAwaitingSavedCodes` is declared, implemented by every store, the in-memory one included, and never called by the library.
- **MFA.** The single-call `ConfirmEnrolment` reads the pending enrolment and then calls the store's `Confirm`. `Confirm` is conditioned on the generation it read, so a new begin landing in between confirms nothing. It is not conditioned on the device proof, and `ConfirmEnrolment`'s godoc names that as a known limit.
- **The established design** carries the username as the token subject, and judges a signing key's age by its creation time alone. Decisions 3 and 4 depart from it; the others have no counterpart there to follow or depart from.

## Decisions

### 1. A queued-sender worker that ends abnormally is replaced

- **The defect.** `recover` cannot stop `runtime.Goexit`, so a wrapped sender that ends its goroutine (as `t.FailNow` does) kills the worker delivering its message. Once every worker is gone, `Send` still queues messages and returns no error, and nothing delivers them. This breaks `email-notification`'s rule that an accepted message is delivered. It was REPRODUCED by a scratch test while `idiomatic-api-shape` was implemented, and is older than that change. The scratch test is not in the tree; task 1.1 writes the red test again.
- **The fix.** A deferred check notices a delivery that did not return normally. It logs the failure and starts a replacement worker, so the pool stays at its configured size. The message being delivered is reported as failed, as a panic's message already is.
- **Order and record (2026-11-03).** The replacement starts before the failure is logged, so a log handler that blocks or itself ends the goroutine cannot shrink the pool. The record has a fixed reason (`goexit`) and carries nothing from the wrapped sender, as a recovered panic's record does.
- **Default and override:** automatic, with no option. A pool that silently shrinks has no use a consumer could want.
- **Alternative considered:** document the case and leave it. Rejected, because the sender would then accept messages it never delivers.
- **Order:** the `email-notification` delta copies the requirement as `idiomatic-api-shape` modified it. That change is archived (2026-10-31), so the base is current.

### 2. A missing sender address stays a configuration error

- **The mismatch.** `notify/smtp.go` wraps `ErrConfig` when a message has no `From` and the sender was built with no default address. `ErrConfig`'s godoc says it marks wiring mistakes, as opposed to failures at send time, and does not mention this case. UNREPRODUCED: the wording disagrees with the behaviour, and the behaviour is not wrong.
- **The decision.** The case is a wiring mistake: the consumer configured neither a default sender nor a sender on the message. `ErrConfig` keeps wrapping it, and its godoc names it.
- **Default and override:** unchanged. A consumer sets `WithSMTPFrom`, or `Message.From`.
- **Pinned in the spec (2026-11-03).** The `email-notification` delta now states that the error is identifiable as a configuration error, so the godoc and the spec say the same thing.
- **Alternative considered:** a new sentinel for a missing address. Rejected, because it adds API for a case the existing sentinel already means.

### 3. The token subject is the user's identifier by default

- **The problem.** Issued tokens carry the principal's username as `sub`. A rename invalidates the user's live tokens, and a username can be reassigned to someone else, while `sub` is the claim every verifier keys on.
- **The decision.** By default the generator writes `Principal.ID` as `sub`, and the JWT authenticator builds the principal with that identifier. This departs from the established design, which carries the username. The departure exists because `sub` is meant to be stable and never reassigned, and a public claim cannot change after the first tag without breaking live tokens and external verifiers. `oidc-provider` relies on it: an OpenID Provider's `sub` must never be reassigned.
- **Default and override.** The default is the user identifier. A consumer whose own systems read the username sets `token.WithUsernameSubject()` on the generator, `authenticate.WithJWTUsernameSubject()` on the authenticator, and `httpsec.WithBearerUsernameSubject()` on the chain's signed bearer. Each option's godoc names the others and says they must agree.
- **Mismatch fails at construction where it can be seen (user's choice, 2026-11-03).** The chain is given token generators through its endpoint options: login, magic link, passkey login, MFA, re-authentication, the OIDC handoff and renewal. Building a chain with signed bearer tokens fails with a configuration error when any of them reports a subject mode other than the bearer's (`library-design.md` rule 6). The check sits beside the existing `checkBindingGenerator` (`httpsec/dpop.go`), which already vets each of those generators at build time. For it, `token.Generator` gains a required method reporting its mode: a typed `token.SubjectMode`, whose zero value is the user identifier. The binding check can use an optional interface (`token.ConfirmingGenerator`), because binding is opt-in, and a generator that lacks it is refused only when binding is on. The subject check applies to every chain, so an optional interface would leave it two choices for a generator that lacks it: refuse every such generator, which is a required method in effect, or skip the check silently (rule 4). It follows the precedent `close-security-gaps` set for `Request.HeaderValues`. It is **BREAKING** for a consumer's own generator, and free before the tag. The standalone `authenticate.JWTAuthenticator` is checked when its verifier is itself a generator, as the chain's bearer is (user's choice, 2026-11-04, from the review of #68). A wrapped verifier, or one that is not a generator, cannot be checked, and its godoc says so. REPRODUCED by task 6.2's red step: the disagreeing rows of `TestNewJWTAuthenticator_SubjectModeAgreement` built without error. A consumer who really issues and reads different subjects gives the provider a verifier that is not the generator.
  - *Alternatives considered:* the option alone, with no check, rejected because a mismatch would surface only as refused tokens at runtime; and the chain following its generator with no option of its own, rejected because a verify-only chain has no generator to follow.
- **Refusal.** Issuing for a principal whose chosen subject is empty fails, instead of minting a token no one can resolve. `token.ErrNoSubject` already refuses an empty username. It now follows the chosen subject: under the default, an empty identifier is refused. Its text, the `token` package doc's "The subject" and `Claims.Subject`'s godoc in `token/claims.go`, and `Generator.Generate`'s godoc in `token/generator.go`, currently say "username" and change with it (corrected 2026-11-03).
- **Bearer paths and their effects.**
  - The standalone `authenticate.JWTAuthenticator` builds its principal from the claims alone. Under the default it carries the identifier and no username.
  - The `httpsec` chain's session-backed bearer interceptor reloads the user and builds the principal from the reloaded details (`PrincipalFromDetails`), so `Username` stays filled. It used to reload by username, keyed on `sub`. Under the default it reloads by the session's user reference instead (`resolve`, through `LoadByUserID`), and refuses a token whose `sub` is not that reference, before any reload. Under `httpsec.WithBearerUsernameSubject()` it looks the user up by username (`admitSubject`, through `LoadByUsername`). The `lookupByUsername` and `lookupBySessionUser` helpers this decision first named were removed once nothing chose between them. The `http-security-chain` delta (added 2026-11-03) states both, and scopes the scenario "Username reassigned to another user" to the username option, since a default token names no username. Either way the user must still own the session, as now. Since `close-security-gaps`, this interceptor checks the session's key binding against the token's `cnf` claim before the reload. The subject check is added beside it, and the binding check is unchanged.
  - The chain's session-reference bearer (`httpsec/session_bearer.go`) carries no token subject. It reloads by the session's user reference, so it is unaffected (noted 2026-11-03).
  - Anything reading `Principal.Username` behind the chain, such as a password re-proof, therefore keeps working.
- **Risk.** A reader of `Principal.Username` behind the standalone authenticator sees an empty name under the default. The first task audits every such reader with gopls before the change, and reports any consumer of the name.
- **Audit outcome (task 2.1, 2026-11-03).**
  - *Standalone authenticator.* No code in the repository consumes `JWTAuthenticator`'s principal, so the empty name reaches consumer code only. The authenticator's godoc says so.
  - *Chain.* Both bearers go through `sessionResolver.resolve`, which builds the principal with `PrincipalFromDetails` from the reloaded user, so every reader behind them sees a filled name: the per-request policy input, the password-change attempt reset, the password re-proof and the default sign-in notice recipient. The session-reference bearer reads no subject, as stated above. `Principal.Username` is also read in `httpsec/reauth_verify.go`, `httpsec/session_renewal.go` and `httpsec/apikey.go`. None of those receives the standalone authenticator's principal.
  - *Other readers of the subject.* `Claims.Subject()` has three production callers: two in `authenticate/jwt.go` and one in `httpsec/bearer.go`. No OIDC handoff, renewal, rate-limit, lockout or audit code reads it.
  - *Corrections.* The chain receives generators through eight entry points, and the list above omitted recovery: `FormLoginDeps.Tokens`, `SessionRenewalDeps.Tokens`, `WithMagicLinkTokens`, `PasswordlessTokens`, `WithMFATokens`, `WithReauthenticationTokens`, `WithRecoveryTokens` and `WithOIDCTokens`. The subject check covers all eight.
  - *Order of the request-time subject check (2026-11-03).* It runs inside the bearer's `admit` step: after the session has loaded and its key binding has been checked, and before the proof is recorded. Inside `admit` because a session only a late renewal may recover carries nothing else to the renewal endpoint, so a check placed after `resolve` would be skipped there. Before the proof because a refused request consumes nothing. After the binding check because a credential presented by the wrong sender is answered as that, whatever it names. A token with no subject is refused the same way in both modes.
  - *Under usernames (2026-11-03).* Review REPRODUCED that the username option fell short of this: a token whose username was renamed or reassigned, refused on a live session, could renew a session only a late renewal may recover, and a refused username consumed the proof (now pinned by `TestBearer_SubjectIsTheSessionUser`, rows "Late renewal under usernames with a username that is not the session's user's" and "Subject refusal under usernames consumes no proof"). So under usernames `admit` loads the user and compares its identifier with the session's, before the proof is recorded, and returns that record for the ordinary path and the renewal endpoint to use, so a late renewal loads the user once (2026-11-04, task 6.7; it passed the record through a field on the resolver, and loaded twice on renewal, REPRODUCED by that task's red step). That record comes from the bearer's user loader rather than the renewal endpoint's, which matters only to a consumer who wires two different ones. Every other renewal still loads twice, in every mode, once to resolve the request and once at the renewal endpoint: the task covers the late path alone. The alternative of carrying the lookup to the renewal endpoint fixes only the first.
  - *A ninth generator route, and two bearers (2026-11-03).* A generator given as the bearer's own `Verifier` is checked too; a wrapped verifier cannot be seen, and the godoc says so. Two signed bearers on one chain that disagree on the subject mode fail to build, whatever their schemes: no generator could agree with both, and the second would refuse every token the first accepts. A consumer migrating subjects does it with one mode at a time.
  - *A principal with no identifier (2026-11-03).* A login refuses it in every mode, not only by way of `token.ErrNoSubject` on a default chain, and an empty user reference matches no user. Review REPRODUCED that otherwise a username or session-reference chain stored a session with no user, and an empty reference matched an empty identifier (now pinned by `TestLogin_PrincipalWithNoIdentifier` and `TestBearer_EmptyUserReferenceMatchesNoUser`). A consumer whose provider returns only a username must supply the identifier; it fails loudly at login instead of quietly storing an ownerless session. Where the chain's login tail meets it, the answer is a server-side failure matching `token.ErrNoSubject`, status 500, in every mode, with a sampled ERROR record of fixed text, because it is a wiring fault that otherwise leaves no signal under the default handler. A provider returning no authentication at all is treated the same. Where a library component judges first, the magic-link manager, a passkey's owner check or recovery, the login fails with that component's own uniform refusal instead. Either way nothing is stored and nothing is handed out.
  - *Basic, and the failure count (user's choice, 2026-11-04, from the review of #68).* A provider given directly to Basic that returns no authentication or no principal gets the same answer: status 500, matching `token.ErrNoSubject`, with a sampled ERROR record of fixed text and no challenge header. REPRODUCED by task 6.1's red step, `TestBasic_ProviderReturningNoAuthentication`: no authentication panicked with a nil dereference at `httpsec/basic.go:251`, and an authentication with no principal succeeded. Form login cleared the failures in both cases, `TestLogin_ProviderReturningNoAuthentication`. A 401, as `FirstOf` answers, was rejected, because it would read as a wrong password and hide a broken provider. Neither Basic nor form login clears the username's failures in this case, since nothing proved the password. *Default and override:* a provider that means "not found" returns `authenticate.ErrAuthenticationFailed`, or is wrapped in `FirstOf`, and gets the uniform refusal. A non-nil principal with no user identifier is not refused on Basic: it creates no session, and this decision covers logins. Form login with such a principal does clear the failures before it answers 500 (noted 2026-11-04, from the group 6 review): the provider did accept the password, so the clearing is deliberate, and what is refused is the wiring.
  - *One identifier check per path (2026-11-04).* `completeLogin` checks before its side effects, and redemption checks for itself, so `prepareLogin` no longer repeats it.
  - *Placement of the build check.* It sits beside `checkBindingGenerator`, not inside it, because that function returns early when no binding is enabled, and the subject check applies to every chain with signed bearer tokens. A session-reference chain refuses generators outright, so it has nothing to check. A nil generator, which `WithOIDCTokens` allows alongside a callback success handler, has nothing to check either.
- **User's choice, 2026-10-31:** an option, defaulting to the identifier.

### 4. Housekeeping deletes the keys it retires for age

- **The problem.** `signingkey.KeyStore` has no delete method. Housekeeping stops publishing old keys but leaves them in the store, which gains a row per algorithm per rotation, hourly by default, and every row is loaded at start and on each reload.
- **The decision.** `KeyStore` gains `Delete(ctx context.Context, kids ...string) error`. It is idempotent: a missing key is not an error. Housekeeping deletes every key it stopped publishing because it passed its retire time, once its grace has passed (both defined below). Such a key can no longer verify a token, since token lifetimes are capped below the key lifetime. A key it stops publishing because it is dated in the future is only unpublished, never deleted, because that date may come from another replica's clock. A failed delete is reported to the logger and the error hook and retried at the next run.
- **How housekeeping finds them (2026-11-03).** From the store's own listing at each run, not from what this run unpublished, so a failed delete is found again after a restart, and a key this replica never held still goes. That adds one `LoadAll` per run, against sixty reloads an hour. A failed listing is reported and retried like a failed delete; unpublishing does not depend on the store.
  - *Dropped (user's choice, 2026-11-04).* The review of #68 suggested deciding from the manager's latest listing instead, saving about one load in sixty-one, on the reasoning that staleness can only delay a delete. Implementing it REPRODUCED the opposite: a key removed by hand or by a backup restore, with no reload since, still counted as the newest key and as a successor, so the newest stored key was deleted and the store left empty (`TestHousekeeping_Retention`, row "Key removed from the store since the last reload"; `TestRetireTime`, row "Deletion judges a key's successor from the listing alone"). Both rows passed once `deleteRetired` listed the store itself again. The harm looked small, since the key deleted is already past its grace (reasoned, not tested), but an unconditional guarantee is worth more than that saving.
- **Shutdown is not a failure (user's choice, 2026-11-04, from the review of #68).** The background work's context ends only when `Shutdown` cancels it, so a store call that fails once it has ended is not reported, for rotation, reload and housekeeping alike. Housekeeping's store calls are new in this change; the other two predate it, and share `km.report`, so covering one would leave the same alarm in the others. REPRODUCED by task 6.3's red step: all three shutdown rows of `TestShutdown_StoreCallIsNotReported` fired the hook and wrote an ERROR record. *Default and override:* none. The hook and the logger still receive every failure while the work is running.
- **What is never deleted (2026-11-03).** A current key of this manager, the newest stored key of each algorithm, and a key dated in the future. The newest-key guard covers every listed algorithm, not only the ones this manager signs with, because another replica may be signing with that key. Unpublishing stays as the settled spec has it: a foreign key past its lifetime leaves the published set either way. REPRODUCED in review before this rule, and now pinned by `TestHousekeeping_Retention`, row "Retired key of an unconfigured algorithm".
- **Reload (2026-11-03).** A manager drops a held key that has passed its retire time once the store no longer lists it, so a replica already holding a deleted key stops publishing it. A held key that has not passed its retire time stays published whether listed or not.
- **Every replica must agree.** `WithRetiredKeysKept`, `WithKeyLifetime`, `WithRetiredKeyGrace`, the rotation interval and the reload interval only hold if every replica sharing a store sets them alike, since each enters the rule. A replica rotating every 12 hours refuses a valid token that one rotating hourly accepts; a `TestRetireTime` row pins this as a documented limit. Their godocs state it.
- **A key retires when its tokens can have expired (user's choice, 2026-11-03).**
  - *The problem.* Review REPRODUCED that a key which stayed current past its lifetime, because rotation kept failing, was unpublished and deleted as soon as rotation recovered, while a token it signed seconds earlier was still valid (now pinned by `TestRetireTime`, row "A stale current key displaced by its rotation keeps verifying"). So "Such a key can no longer verify a token" above held only for a key replaced on time. Unpublishing is what refuses those tokens, and it did so before deletion existed: delaying the delete alone would save none of them, because a restarted replica does not publish a key past the rule either.
  - *The decision.* A key's retire time is one reload interval after the later of its creation plus the key lifetime, and its successor's creation plus the key lifetime minus the rotation interval. `token`'s construction already caps a token's lifetime at that window. The reload interval is there because a replica may go on signing with a replaced key until its next reload (user's choice, 2026-11-03; without it a token at the cap was refused with nearly its whole last reload interval to live, now pinned by `TestRetireTime`, row "A replica still signing before its reload"). A key replaced on time therefore retires one reload interval later than it did before, one minute by default. The cost is one more minute in the published set, and it needs no change to `token`'s cap or `LifetimeReporter`, as tightening the cap would. Publishing, reload, construction and deletion all use this one rule. The store write that makes a successor visible can add latency of its own, which is not covered: UNREPRODUCED, and bounded in practice by how long a store write takes. The margin also closes a corner review found with a lifetime barely longer than the rotation and a grace of zero: another replica's current key could be deleted before its next reload. REPRODUCED against the rule without the margin, and gone with it (`TestRetireTime`, row "A lifetime barely longer than the rotation leaves another replica's current key until its reload"), so construction does not refuse that configuration.
  - *Successor.* The next newer stored key of the same algorithm, not counting a key dated later than the present time plus the reload interval, so a far-future key cannot hold every older key back. It comes from the listing, so it needs no new field and no port or schema change, and it survives a restart. A manager remembers its last listing, under its lock, so housekeeping needs no store call to judge a held key, and a successor the store lists but no manager can decode does not make a key's publication flap on every run.
  - *Stated limit.* The rule is read from the store, so removing a live key by hand makes the next newer key its predecessor's successor, and can bring back an already retired key; a `TestRetireTime` row pins this as a documented limit. Housekeeping's own deletes cannot cause this, because a key is deleted only after its retire time. A second route is accepted on purpose: an unconfigured algorithm's newest key, kept in the store by the newest-key guard, comes back for one window when a successor later appears, including when a far-future key's date arrives (`TestRetireTime`, row "A retired key of an unconfigured algorithm comes back for one window when a far-future key's date arrives"), since its tokens may be live. A configured algorithm's key is current in that position, so this reaches only a key this manager does not sign with, and bounding it would add a rule for a rare case. A replica that cannot reload goes on signing with a replaced key past the margin; a failing reload is reported. The package doc states all of these.
  - *Departure.* The established design judges a key by its creation time alone. The departure exists because that refuses valid tokens after a rotation outage, shown by the failing test above.
  - *Alternative considered:* document the loss. Rejected, because it leaves a known hole in a guarantee that is cheap to close before the tag.
- **Deletion waits out a grace (user's choice, 2026-11-03).**
  - *The problem.* Review REPRODUCED that a replica with a skewed clock deletes keys others still sign with or need, so a restarted or newly scaled replica cannot publish them, and that a replica with a shorter lifetime does the same to a longer-lifetime replica (now pinned by `TestRetireTime`, rows "Replica with a fast clock leaves keys in place", "Replica with a slow clock leaves its key in place" and "Replica with a shorter lifetime"). A bad clock could only harm its own host before deletion existed.
  - *The decision.* A key leaves the store one grace after its retire time. The grace defaults to one key lifetime. With the defaults, the skew needed to delete a signing key rises from about 23 hours to about 47 hours (`TestRetireTime_SkewNeededToDeleteASigningKey`), and the skew needed to lose a default 15-minute token to about 46 hours 46 minutes. A token at the lifetime cap has less room: about 24 hours, just over the grace (a review scratch test at about 25 hours of skew lost it, and is not kept in the tree). All of those are a host badly misconfigured rather than drifting, and the harm is reduced, not bounded: the godoc says replicas sharing a store must keep synchronised clocks and be configured alike.
  - *Default and override.* The default is one key lifetime. `WithRetiredKeyGrace(d)` replaces it, and zero deletes at the retire time. A negative grace, or a grace together with `WithRetiredKeysKept()`, fails at construction (`library-design.md` rule 6).
  - *Cost.* About twice as many rows, roughly 48 per algorithm at hourly rotation, all loaded at each reload.
  - *Alternatives considered:* the database's clock, the only choice that bounds the risk, rejected because every consumer's store would have to supply a time source and an in-memory store has no database; and documentation alone, rejected because the loss is permanent.
- **Implementations.** The in-memory store, `sqlstore`, `pgxstore`, `gormstore`, and the sealing decorator, which forwards the call. The three SQL stores share one `internal/storekit` helper for which identifiers can be stored and how they are bound. The store conformance suite gains delete cases.
- **A reload with nothing to drop (2026-11-04).** `dropUnlistedLocked` computes no retire times when every held key is listed. Task 6.5 measured it with `BenchmarkReload_RetiredKeysKept`, 10 runs each, compared with `benchstat`: at 1000 keys a reload fell 19.63%, from 626.2µs to 503.2µs, with 26.20% fewer bytes per run (p=0.000). The gain is significant and modest, and reloads run once a minute by default. It stays because the guard is one cheap check.
- **Default and override.** Deletion is on by default. `WithRetiredKeysKept()` keeps retired keys in the store, for a consumer who audits them.
- **User's choice, 2026-10-31:** add the delete method before the tag.

### 5. The unused passkey store method is removed

- `passkey.CredentialStore.DeleteAwaitingSavedCodes` has not been called by the library since an earlier change stopped deleting credentials awaiting saved codes. It is removed from the port, the in-memory `MemoryCredentialStore` (added to this list 2026-11-03), the three SQL stores, `internal/pgschema`, the conformance suite and the mocks. Removing a port method after the tag would break every consumer store, so it goes now.
- **Default and override:** none; it is a removal of an unused method.
- **User's choice, 2026-10-31.**

### 6. The reported MFA confirmation race is settled before the tag

- **The claim.** The single-call `ConfirmEnrolment` reads the pending enrolment, then calls the store's `Confirm`. A device proof of the same generation landing in between would go unseen, and the enrolment would be confirmed alongside it. UNREPRODUCED.
- **Corrected 2026-11-03.** The claim as first recorded said `Confirm` checks the generation too. It does not need to: `Confirm` takes the generation it read, so a new begin landing in between already confirms nothing. Only the device proof is unconditioned. `ConfirmEnrolment`'s godoc names that as a known limit, for consumers who expose both this call and the enrolment path to one session. The red test is therefore expected to fail. The claim stays UNREPRODUCED until it does, for the reason claimed.
- **The decision.** The first task of its group writes the red test. If it passes, the claim is dropped and recorded here. If it fails, apply pauses so that this decision and a `multi-factor-auth` delta can be written before the fix, because fixing it changes the store's `Confirm` contract.
- **User's choice, 2026-10-31.**
- **Result, REPRODUCED (2026-11-03).** `TestConfirmEnrolment_DeviceProofBetweenReadAndConfirm`, in `authenticate/mfa/confirm_race_test.go`, run with `go test -race -run TestConfirmEnrolment_DeviceProofBetweenReadAndConfirm -count=10 ./authenticate/mfa/`. Its row `proof_lands_between_the_read_and_Confirm` failed 10 of 10:
  ```
  Expected error with "mfa: invalid code" in chain but got nil.
  Should be true (the enrolment must stay pending until the emailed code is redeemed)
  Expected value not to be nil. (the emailed code must stay outstanding)
  ```
  `ConfirmEnrolment` returns nil, and the enrolment reads as confirmed with its emailed code wiped, so it is confirmed without proof of the mailbox, and the user's real code is then refused. This breaks the `multi-factor-auth` scenario "No other way round the emailed code". The rows for a proof before the read, a proof after confirmation and no proof all pass on the same assertions. A disposable overlay adding the condition to the in-memory store's `Confirm` turned the failing row green. It needs a consumer's own out-of-band confirm route running at the same time as an enrolment-path proof on one enrolment, which bears on urgency and not on whether it is a defect.
- **The fix (user's choice, 2026-11-03).** The store's `Confirm` also requires that the enrolment has no device proof, inside its one conditional write. A proof landing after `ConfirmEnrolment`'s read now makes `Confirm` report false, so the call returns the invalid-code error and the enrolment stays pending, with any emailed code still redeemable. The same holds with email confirmation off, and for a store whose reads lag its writes, because the write decides. `ConfirmEnrolment`'s godoc drops its known limit.
- **What follows from it.**
  - `Confirm` no longer clears an emailed code, since only a device proof issues one and `Confirm` now refuses every proven enrolment. The clearing is removed rather than kept as a defence that could never run. The spec's rule that `Confirm` never lowers the recorded step goes for the same reason: `AcceptStep` needs a confirmed enrolment, a proof now blocks `Confirm`, and a new begin clears the step, so nothing can reach it through the port. The stores keep their forward-only write all the same, as an uncontracted safety net against replaying a proving code: removing it would change three statements and their rows for no behaviour, and the comments on it say it is a safety net, not a guarantee.
  - The `security-state-stores` scenario "Confirmation keeps a later device-proof step" pinned the old contract. It keeps its name and now states a refusal, with the later step and the emailed code left in place. Its reason for existing, that a proving code is never accepted again, still holds: an unconfirmed enrolment accepts no verification, and `AcceptStep` keeps the step moving forward once the path completes it.
  - `store-conformance` gains a case that catches a store ignoring the proof.
- **What this does not close (2026-11-03).** Once a proof is recorded on a generation, the single-call confirm cannot confirm that generation. It carries no mailbox proof of its own, though: a begin followed by a valid code confirms, as the out-of-band contract says, and so does begin, prove, begin again, then confirm, since a new begin clears the proof (pinned by the `multi-factor-auth` scenario "A new begin clears the proof the confirmation would have met"). The godoc and the README therefore say the call must never be reachable from a session the enrolment path confines. No route in the library exposes it; a consumer's own route does. Enforcing this, for example by marking generations begun through the path, would change the store contract, and is not done here.
- **Departure from `mfa-enrolment-path`.** That change kept `Confirm`'s contract unchanged so stores built against it kept their semantics, and left this condition to a change of its own. This is that change. A store that does not implement `DeviceProofStore` has no device proofs, so its enrolments behave as before. A consumer's store that implements the port must add the condition, and the conformance suite says so. **BREAKING** for those stores, and free before the tag. After the tag it would not be.
- **Default and override:** none. It is a guarantee of the emailed code, not a policy. A consumer who wants no emailed code already has the explicit option that turns email confirmation off, and the single-call confirm still serves enrolments with no device proof.
- **Alternatives considered:** stating the limit in the spec, rejected because it writes a way round the mailbox proof into a security requirement and closing it after the tag would break every consumer store; and a separate change, rejected because nothing in the work depends on this one's other items and the store contract is what this change exists to settle before the tag.

## Risks / Trade-offs

- **[Decision 3 changes what every verifier of a scrty token reads as `sub`]** → Nothing is tagged, so no external verifier exists yet. The username option keeps the old reading for a consumer who needs it, and the changelog's first entry names the change.
- **[A reader of `Principal.Username` behind the standalone authenticator sees an empty name]** → Task 2.1 audits every such reader with gopls before any code changes.
- **[Decision 6 grew the change]** → The race reproduced, and the fix changes `EnrolmentStore.Confirm` for every store. The rest of the change does not depend on it and may land first. The red test stays uncommitted until its fix lands with it.
- **[Overlap with `close-security-gaps` on `token-issuance`]** → Resolved. That change added a requirement, this one modifies another, and it was archived on 2026-11-03. On the same day, each MODIFIED requirement here was compared with its synced spec, and only the intended changes differ.
